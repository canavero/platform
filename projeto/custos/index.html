    Custos, PaaS e SLA

    1. Premissas

    • Região us-east-2 (Ohio), a do enunciado. Os preços abaixo são iguais em us-east-1 (N. Virginia) para todos os itens usados.
    • Preços on-demand, mês de 730 h, em USD, consultados em 15/11/2026 na AWS Price List (EKS, ELB, EC2, RDS e IPv4 público conferidos nos arquivos oficiais; NAT Gateway, EBS e ElastiCache pelas páginas de preço de cada serviço). Impostos não incluídos.
    • Arquitetura exatamente como os scripts criam (cenário A): template de VPC do enunciado com 1 NAT Gateway, 2 nós t3.medium Spot, Postgres e Redis dentro do cluster, imagens no ECR e 1 Classic Load Balancer (Service LoadBalancer do gateway). O primeiro deploy (2 NAT, nós on-demand, RDS) está no cenário A0, para comparação.

    A troca foi feita com o cluster no ar: o node group Spot subiu ao lado do antigo, o EKS drenou os pods para ele, e o ELB seguiu respondendo 200. O smoke test pelo ELB deu os mesmos 11/14 de antes (as 3 falhas eram do câmbio, por falta da API key da AwesomeAPI; com a chave no Secret, 14/14).

    Avaliado e não aplicado:

    Ideia Economia Por que não
    Nenhum NAT (nós nas subnets públicas, com IP público) −0,04/h o enunciado põe os pods em subnets privadas, e os nós ficariam expostos com IP público
    1 nó só −0,01/h o HPA do gateway não passaria de ~3 réplicas (falta memória: cada réplica pede 384 Mi). Fora da gravação dá para usar desiredSize=1 (o mínimo do node group já é 1)
    t3.small (2 GiB) −0,01/h 4 JVMs × 384 Mi + Postgres já lotam 2 nós; o HPA ficaria Pending
    Tirar o Load Balancer (NodePort/port-forward) −0,035/h o enunciado pede acesso público pelo LB
    Fargate no lugar dos nós — cobra por pod: ~15 pods × (0,25 vCPU + 0,5 GB) ≈ US$ 0,19/h, contra US$ 0,02/h dos 2 nós Spot

    O que o Spot e o Postgres no cluster custam em confiabilidade

    • Spot: a AWS pode retomar um nó com 2 min de aviso. O EKS drena o nó, e os pods sobem no outro (ou no substituto que o node group cria). Com 2 tipos de instância e 2 AZs, o risco de ficar sem capacidade é baixo. Para dev/teste e para o vídeo, é aceitável.
    • Postgres no cluster (Deployment sem volume persistente): se o pod for recriado, os dados somem, e o account precisa reiniciar para o Flyway recriar o schema. Em produção, o cenário C usa RDS Multi-AZ (aws/rds-create.sh continua no repositório e foi validado no primeiro deploy: Flyway migrou, smoke test 11/14).

    O teardown automático não disparou

    O agendamento de segurança rodava no Mac de um integrante e não executou às 01:43 UTC. Às 01:52 conferimos de fora que o Load Balancer ainda respondia 200, entramos na conta pelo AWS access portal e rodamos os passos do aws/eks-teardown.sh no AWS CloudShell (02:18–02:30 UTC). Em seguida, uma varredura em todas as regiões (EKS, EC2, NAT, Load Balancers, IPs elásticos, RDS) voltou vazia. O atraso custou ≈ US$ 0,12 a mais. Lição: o teardown automático precisa rodar num lugar que não dorme (por exemplo, um AWS Budget com ação ou uma regra do EventBridge na própria conta), não num notebook. Evidência: docs/evidencias/teardown.txt.

    Cost Explorer: está habilitado na conta e mostrava US$ 0,00 de 01/11 a 15/11 (consultado às 23:05 UTC de 15/11; nenhum recurso existia antes desta sessão). A AWS publica os custos com ~24 h de atraso, então o valor desta sessão aparece a partir de 16–17/11:

    aws ce get-cost-and-usage --time-period Start=2026-11-15,End=2026-11-18 --granularity DAILY \
  --metrics UnblendedCost --group-by Type=DIMENSION,Key=SERVICE \
  --query 'ResultsByTime[].[TimePeriod.Start, Groups[].[Keys[0], Metrics.UnblendedCost.Amount]]'

    Outras alavancas para um ambiente que fique ligado: Savings Plans de 1 ano (~30–40 % em EC2), nós Graviton (t4g.medium Spot, com PLATFORMS=linux/arm64 no push-images.sh) e desligar fora do horário (desiredSize=0 no node group; o control plane continua cobrando).

    3. ECR × Docker Hub

    Amazon ECR (usado no EKS) Docker Hub (alternativa)
    Custo US$ 0,10/GB-mês (≈ US$ 0,20 aqui, limitado pela lifecycle policy); pull na mesma região grátis grátis (repositórios públicos)
    Limite de pull sem limite prático 10/h por IP sem login; 100/h com login (Personal)
    Privacidade privado, IAM (a role dos nós já tem AmazonEC2ContainerRegistryReadOnly) imagens públicas
    Segurança scan on push (vulnerabilidades) grátis —
    Integração nativa com EKS, IAM e OIDC do GitHub Actions qualquer cluster/CI

    No deploy real usamos o ECR da conta do grupo: não havia Docker Hub configurado, o pull não tem limite, as imagens ficam privadas e os nós autenticam pela role do node group, sem segredo no cluster. O custo é de centavos. O Docker Hub (padrão do hands-on 4) continua funcionando com DOCKERHUB_USERNAME=<usuario> nos scripts e no CI.

    Serviço Modelo Como foi usado O que deixamos de gerenciar
    Amazon EKS CaaS/PaaS control plane do Kubernetes instalação, HA, backup do etcd, upgrades do API server
    Managed node group IaaS gerenciado nós EC2 com AMI otimizada provisionamento e substituição de nós, drain em upgrades
    Elastic Load Balancing PaaS criado automaticamente pelo Service LoadBalancer servidores de balanceamento, health checks, escala do LB
    Amazon RDS PaaS (DBaaS) PostgreSQL 17 em subnet privada no primeiro deploy (validado e depois removido para cortar custo; volta no cenário C) patches, backups, failover Multi-AZ, storage
    Amazon ECR PaaS (registry) imagens privadas dos 4 serviços, scan on push servidor de registry, storage, autenticação
    CloudFormation PaaS (IaC) VPC do template do enunciado ordem de criação/remoção de 20+ recursos de rede
    GitHub Actions PaaS (CI/CD) build, teste, imagem, deploy servidor Jenkins, agentes, plugins
    GitHub Pages PaaS (hosting) esta documentação servidor web, TLS, CDN
    AwesomeAPI SaaS (API) cotações de câmbio; a partir da AWS exige API key (grátis até 100 mil req/mês) coleta e atualização das cotações

    Alternativas mais "PaaS": rodar os 4 contêineres no ECS Fargate (sem nós nem control plane pago: 4 tarefas de 0,25 vCPU / 0,5 GB ≈ 4 × (0,25 × 0,04048 + 0,5 × 0,004445) × 730 ≈ US$ 36/mês + ALB) ou no App Runner (escala até zero requisições). O EKS foi mantido por ser o requisito da disciplina e pela portabilidade (os mesmos manifests rodam em minikube/kind ou em outra nuvem); o custo fixo do control plane (US$ 73) é o preço dessa portabilidade.

    SLAs dos componentes AWS (mensais, publicados pela AWS)

    Componente SLA
    Elastic Load Balancing 99,99 %
    Amazon EKS (API do cluster) 99,95 %
    Amazon EC2 (nível de região, instâncias em ≥ 2 AZs) 99,99 %
    Amazon EC2 (instância individual) 99,5 %
    Amazon RDS Single-AZ 99,5 %
    Amazon RDS Multi-AZ 99,95 %

    Disponibilidade composta (componentes em série)

    $$ A = A_{ELB} \times A_{EKS} \times A_{EC2} \times A_{DB} $$

    Cenário Cálculo Disponibilidade Indisponibilidade/mês
    A0 (RDS Single-AZ) 0,9999 × 0,9995 × 0,9999 × 0,995 99,43 % ≈ 4 h 10 min
    C (RDS Multi-AZ, ≥ 2 réplicas em 2+ AZs) 0,9999 × 0,9995 × 0,9999 × 0,9995 99,88 % ≈ 53 min

    SLO e SLA propostos para a API Store

    Definição Meta
    SLI de disponibilidade requisições ao gateway sem erro 5xx ÷ total, janela de 30 dias —
    SLI de latência p95 de GET /exchanges/* (com cache) —
    SLO (interno) disponibilidade 99,5 % (orçamento de erro: 0,5 % ≈ 3 h 36 min/mês, ou 5.000 erros a cada 1 milhão de requisições)
    SLO (interno) latência p95 < 300 ms
    SLA (contrato) disponibilidade mensal 99,0 % — abaixo disso, crédito de 10 % (25 % abaixo de 95 %)

    O SLA é mais folgado que o SLO de propósito: o SLO dispara a reação (congelar deploys, priorizar confiabilidade) antes de o contrato ser quebrado — como na aula SLI/SLO/SLA. O SLO de 99,5 % também é compatível com o cenário A0 + RDS Single-AZ (99,43 % de piso teórico só seria um problema em um mês com falha longa do banco). O cenário A atual é de dev/teste e não promete SLA. Para garantir 99,5 % com folga, use o cenário C.

    SLIs medidos com as métricas que o projeto já exporta para o Prometheus:

    # disponibilidade (30 dias)
1 - sum(rate(http_server_requests_seconds_count{job="GatewayMetrics",status=~"5.."}[30d]))
  / sum(rate(http_server_requests_seconds_count{job="GatewayMetrics"}[30d]))

# taxa de queima do orçamento (alerta se > 14,4 por 1 h — consome 2 % do orçamento)
(sum(rate(http_server_requests_seconds_count{job="GatewayMetrics",status=~"5.."}[1h]))
  / sum(rate(http_server_requests_seconds_count{job="GatewayMetrics"}[1h]))) / 0.005

    O que no projeto protege o SLO: readiness probes + rolling update (deploy sem downtime), circuit breakers (falha rápida e parcial em vez de cascata), cache (o exchange continua respondendo por até 60 s com a AwesomeAPI fora), rate limiting (protege contra sobrecarga), HPA (capacidade acompanha a demanda) e nós em 2 AZs.
