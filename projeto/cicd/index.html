    CI/CD — GitHub Actions

    O enunciado aceita Jenkins ou GitHub Actions; usamos GitHub Actions (zero infraestrutura, gratuito para repositórios públicos), seguindo o apêndice GitHub Actions da disciplina e as etapas pedidas no exercício Jenkins: SCM → Dependencies → Build → Push da imagem → Deploy to K8s. O registry é o Amazon ECR da conta do grupo (o mesmo usado no deploy real) ou o Docker Hub.

    flowchart LR
    push([push em main]) --> build
    subgraph wf [".github/workflows/ci.yml (cada serviço)"]
        build["Build & Test<br/>checkout + interfaces<br/>mvnw verify"] --> image["Imagem: ECR ou Docker Hub<br/>buildx amd64+arm64<br/>tags :latest e :sha<br/>Trivy"]
        image --> deploy["Deploy EKS<br/>kubectl set image :sha<br/>rollout status"]
    end
    pr([pull request]) --> build
    image -. "só se vars.AWS_ECR ou vars.DOCKERHUB_USERNAME" .- image
    deploy -. "só se vars.EKS_CLUSTER" .- deploy
    Job Quando roda O que faz
    Build & Test todo push e PR checkout do serviço e dos módulos de interface (repositórios irmãos, mvn install), ./mvnw verify (testes + jar), artefato jar
    Imagem push (não PR) e variável AWS_ECR=true ou DOCKERHUB_USERNAME credenciais AWS por OIDC (sem chave fixa), login no ECR (ou Docker Hub), QEMU + Buildx, imagem linux/amd64,linux/arm64, tags :latest e :<sha>, Trivy (HIGH/CRITICAL)
    Deploy EKS push em main e variável EKS_CLUSTER definida mesma role OIDC, aws eks update-kubeconfig, kubectl set image deployment/<svc> <svc>=<imagem>:<sha>, kubectl rollout status

    Sem as variáveis, os jobs de imagem e deploy ficam skipped (não falham) — o pipeline já funciona antes da AWS existir. Os módulos de interface (account, auth, exchange) têm um workflow só de build; o repositório principal tem o E2E (compose + smoke test com os submódulos) e o docs (MkDocs → GitHub Pages).

    api/auth-service/.github/workflows/ci.yml 
    name: CI/CD

on:
  push:
    branches: [main]
  pull_request:
  workflow_dispatch:

permissions:
  contents: read

# Configuração (Settings > Secrets and variables > Actions):
#   Amazon ECR: variable AWS_ECR=true + secret AWS_ROLE_ARN (OIDC, sem chave fixa; ou as access keys)
#   Docker Hub: variable DOCKERHUB_USERNAME + secret DOCKERHUB_TOKEN
#   Deploy:     variable EKS_CLUSTER (ex.: eks-store); AWS_REGION opcional (padrão us-east-2)
# Sem as variáveis, só o job de build/teste roda; os outros ficam "skipped".
env:
  SERVICE: auth
  REPOSITORY: auth-service

jobs:
  build:
    name: Build & Test
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: actions/checkout@v7
        with:
          repository: ${{ github.repository_owner }}/account
          path: deps/account
      - uses: actions/checkout@v7
        with:
          repository: ${{ github.repository_owner }}/auth
          path: deps/auth
      - uses: actions/setup-java@v6
        with:
          distribution: temurin
          java-version: '25'
          cache: maven
      - name: Install interfaces (store:account, store:auth)
        run: for d in deps/*; do (cd "$d" && ./mvnw -B -q --no-transfer-progress install -DskipTests); done
      - name: Test & package
        run: ./mvnw -B --no-transfer-progress verify
      - uses: actions/upload-artifact@v7
        with:
          name: jar
          path: target/*.jar

  image:
    name: Imagem (ECR ou Docker Hub, scan)
    needs: build
    if: github.event_name != 'pull_request' && (vars.AWS_ECR == 'true' || vars.DOCKERHUB_USERNAME != '')
    runs-on: ubuntu-latest
    permissions:
      contents: read
      id-token: write # OIDC com a AWS
    steps:
      - uses: actions/checkout@v7
      - uses: actions/download-artifact@v8
        with:
          name: jar
          path: target
      - uses: docker/setup-qemu-action@v4
      - uses: docker/setup-buildx-action@v4
      - if: vars.AWS_ECR == 'true'
        uses: aws-actions/configure-aws-credentials@v6
        with:
          aws-region: ${{ vars.AWS_REGION || 'us-east-2' }}
          role-to-assume: ${{ secrets.AWS_ROLE_ARN }}
          aws-access-key-id: ${{ secrets.AWS_ACCESS_KEY_ID }}
          aws-secret-access-key: ${{ secrets.AWS_SECRET_ACCESS_KEY }}
          mask-aws-account-id: true # o log de repositório público não mostra a conta
      - name: Login no registry
        env:
          ECR: ${{ vars.AWS_ECR }}
          HUB_USER: ${{ vars.DOCKERHUB_USERNAME }}
          HUB_TOKEN: ${{ secrets.DOCKERHUB_TOKEN }}
        run: |
          if [ "$ECR" = true ]; then
            REGISTRY=$(aws sts get-caller-identity --query Account --output text).dkr.ecr.$AWS_REGION.amazonaws.com
            aws ecr get-login-password | docker login -u AWS --password-stdin "$REGISTRY"
          else
            REGISTRY=$HUB_USER
            echo "$HUB_TOKEN" | docker login -u "$HUB_USER" --password-stdin
          fi
          echo "IMAGE=$REGISTRY/$REPOSITORY" >> "$GITHUB_ENV"
      - name: Build & push (linux/amd64 para o EKS, linux/arm64 para Mac/Graviton)
        uses: docker/build-push-action@v7
        with:
          context: .
          platforms: linux/amd64,linux/arm64
          push: true
          tags: ${{ env.IMAGE }}:latest,${{ env.IMAGE }}:${{ github.sha }}
      # bottleneck: vulnerability scanning (relatório; não bloqueia o pipeline)
      - name: Trivy (HIGH/CRITICAL)
        run: >
          docker run --rm -v "$HOME/.docker/config.json:/root/.docker/config.json:ro"
          aquasec/trivy:latest image --no-progress --severity HIGH,CRITICAL --exit-code 0
          "$IMAGE:${{ github.sha }}"

  deploy:
    name: Deploy EKS
    needs: image
    if: github.ref == 'refs/heads/main' && vars.EKS_CLUSTER != ''
    runs-on: ubuntu-latest
    permissions:
      contents: read
      id-token: write
    steps:
      - uses: aws-actions/configure-aws-credentials@v6
        with:
          aws-region: ${{ vars.AWS_REGION || 'us-east-2' }}
          role-to-assume: ${{ secrets.AWS_ROLE_ARN }}
          aws-access-key-id: ${{ secrets.AWS_ACCESS_KEY_ID }}
          aws-secret-access-key: ${{ secrets.AWS_SECRET_ACCESS_KEY }}
          mask-aws-account-id: true
      - name: Rolling update
        env:
          ECR: ${{ vars.AWS_ECR }}
          REGISTRY: ${{ vars.DOCKERHUB_USERNAME }}
        run: |
          [ "$ECR" != true ] || REGISTRY=$(aws sts get-caller-identity --query Account --output text).dkr.ecr.$AWS_REGION.amazonaws.com
          aws eks update-kubeconfig --name ${{ vars.EKS_CLUSTER }}
          kubectl set image "deployment/$SERVICE" "$SERVICE=$REGISTRY/$REPOSITORY:${{ github.sha }}"
          kubectl rollout status "deployment/$SERVICE" --timeout=300s
    .github/workflows/e2e.yml (repositório principal) 
    name: E2E

# Sobe a plataforma inteira (submódulos) com docker compose e roda o smoke test pelo gateway.
on:
  push:
    branches: [main]
  pull_request:
  workflow_dispatch:

permissions:
  contents: read

jobs:
  e2e:
    runs-on: ubuntu-latest
    timeout-minutes: 20
    steps:
      - uses: actions/checkout@v7
        with:
          submodules: recursive
      - uses: actions/setup-java@v6
        with:
          distribution: temurin
          java-version: '25'
          cache: maven
      - name: Build & test (7 módulos, mvnw)
        run: ./scripts/build.sh
      - name: docker compose up
        env:
          # A AwesomeAPI devolve 429 para IPs de nuvem sem API key: no CI o exchange fala com um
          # stub (setup/provider-stub), e o teste não depende de quota de terceiros.
          EXCHANGE_PROVIDER_URL: http://provider-stub
        run: docker compose --profile e2e up -d --build db redis provider-stub account auth exchange gateway
      - name: Smoke test
        run: ./scripts/smoke-test.sh
      - name: Logs
        if: failure()
        run: docker compose --profile e2e logs
      - name: Teardown
        if: always()
        run: docker compose --profile e2e down -v

    Configuração (uma vez por repositório de serviço)

    Tipo Nome Valor
    variable AWS_ECR true (imagem no ECR)
    secret AWS_ROLE_ARN role github-actions-store (OIDC; Runbook, passo 7)
    variable EKS_CLUSTER eks-store
    variable AWS_REGION us-east-2 (padrão)
    variable / secret DOCKERHUB_USERNAME / DOCKERHUB_TOKEN alternativa ao ECR
    secret AWS_ACCESS_KEY_ID / AWS_SECRET_ACCESS_KEY alternativa ao OIDC (não recomendada)

    A role github-actions-store só aceita tokens dos repositórios *-service na branch main, tem AmazonEC2ContainerRegistryPowerUser + eks:DescribeCluster no IAM e a access policy AmazonEKSEditPolicy restrita ao namespace default — suficiente para publicar imagens e atualizar Deployments, sem poder administrar o cluster. Nenhuma chave de longa duração existe, e o ID da conta não vai para arquivos nem para os logs públicos (mask-aws-account-id: true).

    Execuções no GitHub Actions

    Os workflows rodam no GitHub a cada push (15/11/2026, 23:01 UTC). O repositório principal tem duas cópias idênticas: canavero/platform, onde o E2E e o deploy das docs rodam, e EuMiguelll/Projeto-PMA, a entrega individual do Miguel, que tem os mesmos arquivos em .github/workflows/ mas o Actions desligado (a conta pessoal está com cobrança bloqueada no GitHub). Ali o site é publicado pela branch gh-pages (mkdocs gh-deploy).

    Repositório Workflow Build & Test Imagem + Trivy Deploy EKS
    gateway-service CI/CD ✅ ⏭️ ⏭️
    auth-service CI/CD ✅ ⏭️ ⏭️
    account-service CI/CD ✅ ⏭️ ⏭️
    exchange-service CI/CD ✅ ⏭️ ⏭️
    auth, account, exchange CI (interfaces) ✅ — —
    platform E2E e docs ✅ — —

    ⏭️ = skipped de propósito: os jobs de imagem e deploy só ligam com as variáveis AWS_ECR/EKS_CLUSTER e a role OIDC. Para o deploy real, os mesmos passos rodaram à mão, com os mesmos comandos (push-images.sh → ECR, deploy.sh, kubectl set image), como mostram as evidências. A role OIDC não foi criada: deixaria o ARN da conta do grupo no GitHub e um cluster ligado esperando deploys, o que contraria a meta de usar o mínimo de AWS.

    E2E hermético

    O E2E sobe a plataforma inteira com docker compose e roda o smoke test pelo gateway (14 verificações). Os runners do GitHub recebem 429 da AwesomeAPI quando chamam sem API key, e o teste ficava vermelho por um motivo externo ao código. Por isso, no CI o exchange fala com um stub da AwesomeAPI (nginx com respostas fixas, setup/provider-stub/default.conf), que devolve a cotação de USD-BRL e 404 para pares inexistentes, como a API real. O teste fica determinístico e não depende de quota de terceiros. O provedor real foi validado no EKS (smoke test 14/14 pelo ELB, com a API key no Secret exchange-secrets).

    EXCHANGE_PROVIDER_URL=http://provider-stub docker compose --profile e2e up -d --build \
  db redis provider-stub account auth exchange gateway
./scripts/smoke-test.sh   # 14/14

    Boas práticas aplicadas

    • permissions: contents: read (menor privilégio do GITHUB_TOKEN); segredos só em secrets.
    • Cache do Maven (actions/setup-java com cache: maven).
    • Imagem identificada pelo SHA do commit — rastreável e imutável; o deploy usa o SHA, não latest.
    • Deploy com rollout status: o job falha se os pods novos não ficarem prontos (readiness probe), e o Kubernetes mantém os pods antigos atendendo (rolling update).
    • Lint dos workflows com actionlint e dos scripts com shellcheck antes do commit.
