    Teste de carga

    Objetivo (página Load Testing do enunciado): gravar o teste de carga rodando e o HPA escalando o gateway. O alvo é GET /info do gateway — aberto (sem JWT) e fora do rate limiting, então a carga vira CPU e não 429.

    Pré-requisitos

    • Plataforma no ar (./k8s/deploy.sh) e metrics-server (o eks-create.sh instala).
    • kubectl apontando para o cluster: aws eks update-kubeconfig --name eks-store (com SSO expirado: aws sso login).
    • HPA do gateway já vem no manifest (api/gateway-service/k8s/k8s.yaml): CPU 50 % do request (200m), minReplicas: 1, maxReplicas: 10 — equivalente ao kubectl autoscale deployment gateway --cpu-percent=50 --min=1 --max=10 do enunciado.

    Os 3 terminais

    kubectl get hpa gateway -w
# NAME      REFERENCE            TARGETS       MINPODS   MAXPODS   REPLICAS
# gateway   Deployment/gateway   cpu: 2%/50%   1         10        1

    kubectl get pods -l app=gateway -o wide -w

    (-w é o watch nativo do kubectl: imprime uma linha nova a cada mudança; o macOS não traz o comando watch.)

    ./load-test/busybox.sh
# = kubectl run -i --tty load-generator --rm --image=busybox:1.28 --restart=Never -- \
#     /bin/sh -c "while sleep 0.01; do wget -q -O- http://gateway/info; done"   (x4 em paralelo)
# Ctrl+C para parar. Variáveis: SLEEP=0.005 WORKERS=8 TARGET=http://gateway/health-check

    Alternativa: k6 (de fora do cluster, pelo ELB)

    ELB=$(kubectl get svc gateway -o jsonpath='{.status.loadBalancer.ingress[0].hostname}')
docker run --rm -i -e BASE_URL=http://$ELB -e VUS=150 grafana/k6 run - < load-test/k6.js
# local (docker compose): -e BASE_URL=http://host.docker.internal:8080 -e VUS=20 -e RAMP=20s -e HOLD=1m

    Cenários: info (rampa de VUs no /info, alvo do HPA) e user_flow (login → /auth/me → /exchanges/USD/BRL, que exercita JWT, cache Redis e o rate limiting — 429 é esperado). O resumo final mostra http_reqs, latência p(95) e os checks.

    Roteiro de gravação (≈ 1 min de tela)

    Tempos medidos no EKS (2 × t3.medium) em 15/11/2026:

    Tempo Tela Fala (resumo)
    0:00 3 terminais lado a lado, HPA em 1%/50%, 1 pod "Gateway no EKS com HPA: 50 % de CPU, de 1 a 10 réplicas."
    0:10 inicia ./load-test/busybox.sh "Carga de dentro do cluster no /info, 4 loops sem pausa."
    0:40 TARGETS sobe para ~160%/50% "A CPU passa do alvo; o HPA calcula novas réplicas."
    0:55 REPLICAS 4, pods ContainerCreating → Running "Novas réplicas sobem; o Service distribui a carga."
    1:30 8 → 10 réplicas, TARGETS cai para 30–45% "Com mais pods, a CPU por pod fica abaixo do alvo."
    1:45 Ctrl+C na carga "Fim da carga; depois da janela de estabilização (~4–6 min) o HPA volta para 1."

    Dicas: kubectl top pods -l app=gateway mostra a CPU por pod; o scale-down é lento de propósito (behavior.scaleDown.stabilizationWindowSeconds = 300 s por padrão). Para mostrar o scale-down no vídeo, acelere a gravação nesse trecho. Para recomeçar do zero entre tomadas: kubectl scale deployment gateway --replicas=1 (o HPA aceita, já que está sem carga).

    2. k6 pelo Load Balancer

    load-test/k6.js com 100 VUs (rampa de 30 s, platô de 2 min) no /info + 2 usuários no fluxo autenticado, contra http://<elb>. O k6 rodou como pod no próprio cluster (sem pesar no Mac), mas pelo DNS público do ELB: as requisições saem pelo NAT e entram pelo Classic Load Balancer.

    Métrica Resultado
    Requisições 406.170 em ~3 min (2.215 req/s)
    Latência /info média 37 ms · mediana 22 ms · p95 123 ms · máx. 921 ms
    Erros /info 0,00 % (thresholds p(95)<800ms e rate<0.01 ✓)
    Fluxo autenticado login 100 % · /auth/me 98 % (2 de 180 falharam no pico) · câmbio 0 % (AwesomeAPI devolve 429 para a AWS, ver AWS e EKS)
    HPA do gateway 1 → 4 → 8 → 10 em ~47 s; CPU por pod ainda em ~100–200 % no máximo de réplicas

    Limite encontrado: memória do node group

    Com 5× mais carga que o busybox, os HPAs de account, exchange e auth também subiram, e os requests de memória chegaram a 97 % e 89 % dos 2 nós: 2 réplicas do gateway e 1 do auth ficaram Pending (0/2 nodes are available: 2 Insufficient memory). O HPA escala pods, não nós: no EKS isso exige o Cluster Autoscaler ou o Karpenter (o node group já aceita até 3 nós). Outras saídas: nós t3.large (8 GiB), requests de memória menores para as JVMs ou maxReplicas coerente com a capacidade. Para o vídeo, o busybox do enunciado cabe nos 2 nós (10 réplicas, todas Running).

    Problema encontrado pelo teste: REDIS_PORT=tcp://10.96.x.x:6379

    No primeiro deploy, account, exchange e gateway entraram em CrashLoopBackOff: o Kubernetes injeta em todo pod variáveis de service links de cada Service — o Service redis gera REDIS_PORT=tcp://<ip>:6379, que colidiu com o ${REDIS_PORT:6379} do application.yaml (failed to convert java.lang.String to int). No Docker Compose isso não acontece. Correção: enableServiceLinks: false nos Deployments.

    JVM × HPA

    O pico de CPU da JVM na inicialização também conta para o HPA: após o rollout restart, account e exchange subiram para 2 réplicas sem carga. O startupProbe evita tráfego antes da hora, mas não esse efeito; em produção vale configurar behavior.scaleUp com janela de estabilização ou usar uma métrica de requisições (Prometheus Adapter/KEDA). A redução acontece sozinha após a janela padrão de 5 min.

    // Teste de carga com k6 (https://k6.io) — roda em container, sem instalar nada:
//   docker run --rm -i -e BASE_URL=http://<elb-dns> grafana/k6 run - < load-test/k6.js
// Local (compose):  -e BASE_URL=http://host.docker.internal:8080
// Cenários:
//   info      — rampa de usuários no GET /info (alvo do HPA; rota sem rate limit)
//   user_flow — usuários autenticados: login -> /auth/me -> /exchanges/USD/BRL
//               (exercita JWT, cache Redis e o rate limiting: 429 é esperado sob carga)
import http from 'k6/http';
import { check, sleep } from 'k6';

const BASE = __ENV.BASE_URL || 'http://localhost:8080';
const RAMP = __ENV.RAMP || '1m';   // subida
const HOLD = __ENV.HOLD || '3m';   // platô
const VUS = Number(__ENV.VUS || 100);
const JSON_HEADERS = { headers: { 'Content-Type': 'application/json' } };

export const options = {
  scenarios: {
    info: {
      executor: 'ramping-vus',
      exec: 'info',
      stages: [
        { duration: RAMP, target: VUS },
        { duration: HOLD, target: VUS },
        { duration: '30s', target: 0 },
      ],
    },
    user_flow: {
      executor: 'constant-vus',
      exec: 'userFlow',
      vus: Number(__ENV.USERS || 5),
      duration: HOLD,
      startTime: RAMP,
    },
  },
  thresholds: {
    'http_req_failed{scenario:info}': ['rate<0.01'],
    'http_req_duration{scenario:info}': ['p(95)<800'],
  },
};

export function setup() {
  const email = `k6.${Date.now()}@insper.edu.br`;
  const password = '123@321';
  http.post(`${BASE}/auth/register`, JSON.stringify({ name: 'k6', email, password }), JSON_HEADERS);
  return { email, password };
}

export function info() {
  const r = http.get(`${BASE}/info`);
  check(r, { 'info 200': (res) => res.status === 200 });
}

export function userFlow(user) {
  const login = http.post(`${BASE}/auth/login`, JSON.stringify(user), JSON_HEADERS);
  if (!check(login, { 'login 200': (r) => r.status === 200 })) { sleep(1); return; }
  // o cookie é "Secure": em HTTP o k6 não o reenvia sozinho, então mandamos no header
  const params = { headers: { Cookie: `__store_jwt_token=${login.cookies.__store_jwt_token[0].value}` } };
  for (let i = 0; i < 10; i++) {
    const me = http.get(`${BASE}/auth/me`, params);
    const ex = http.get(`${BASE}/exchanges/USD/BRL`, params);
    check(me, { 'me 200|429': (r) => r.status === 200 || r.status === 429 });
    check(ex, { 'exchange 200|429': (r) => r.status === 200 || r.status === 429 });
    sleep(0.2);
  }
}
